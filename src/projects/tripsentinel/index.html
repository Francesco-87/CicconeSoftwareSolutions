TripSentinel

Personal Safety Check-In Application

  • Industry: Personal Safety
  • Type: Full-Stack Web Application
  • Tech: Java, Spring Boot, React, MariaDB, Docker
View GitHub Repo

Overview

TripSentinel is a privacy-focused personal safety application designed around planned-return verification.

A user creates a check-in session before travelling, hiking, working alone, or entering another situation where someone should verify their safe return.

Instead of relying on continuous location tracking, TripSentinel uses scheduled check-ins and human responder escalation when a user fails to confirm their return.

Challenge

Many personal safety applications depend on continuous location tracking or require the user to actively trigger an emergency alert.

This creates several limitations:

  • Continuous tracking can create unnecessary privacy concerns
  • A user may be unable to trigger an emergency alert
  • Automated alerts may lack human context
  • Friends or family may need manual arrangements
  • Existing solutions may provide more monitoring than needed

The challenge was to design a system that:

  • Verifies planned returns without continuous surveillance
  • Supports scheduled safety check-ins
  • Escalates missed check-ins to a human responder
  • Stores only information relevant to each session
  • Maintains clear responsibility between users and responders

Solution

Architecture

TripSentinel uses a layered full-stack architecture with separate application, persistence, and presentation concerns.

Backend

  • Java
  • Spring Boot
  • REST API architecture
  • Service and repository layers
  • DTO and mapper separation

Database

  • MariaDB
  • Relational data model
  • Flyway migrations
  • Hibernate validation

Frontend & Deployment

  • React
  • Docker
  • Docker Compose
  • Environment-based configuration

The structure keeps business rules separate from HTTP, persistence, and presentation logic.

Domain Design

Core entities

  • Users
  • Roles
  • Responder availability
  • Check-in sessions
  • Check-in methods
  • Session events

Core relationships

  • Users can hold multiple roles
  • Responders define availability windows
  • Sessions connect customers and responders
  • Sessions support multiple check-in methods
  • Session events provide an activity history

The data model supports both operational session management and an auditable history of important session events.

Check-In Session Model

Each safety session represents a defined period during which a user is expected to confirm their safe return.

Session Information

  • Start time
  • Expected return time
  • Latest allowed check-in time
  • Location description
  • Important session notes
  • Selected check-in methods

Session Lifecycle

  • Planned
  • Active
  • Checked in
  • Missed
  • Escalated
  • Cancelled

Human Responder Model

TripSentinel introduces a responder role rather than relying entirely on automated emergency handling.

Responders can define availability periods that determine when they are available to handle safety sessions.

Customer

  • Create safety sessions
  • Select check-in methods
  • Provide session-specific information
  • Confirm safe return

Responder

  • Maintain availability windows
  • Support assigned safety sessions
  • Handle missed check-ins
  • Escalate when required

Administrator

  • Manage users
  • Manage roles
  • Manage system data
  • Support operational administration

Privacy by Design

TripSentinel is intentionally not designed as a live surveillance or continuous GPS tracking application.

  • Location can be stored as a simple description
  • Information is connected to individual safety sessions
  • Continuous user location monitoring is not required
  • Human escalation remains part of the safety workflow

This keeps the system focused on confirming a user's safe return rather than monitoring their movements.

Session Event Tracking

Important actions are represented as session events.

Tracked Events

  • Session created
  • Reminder sent
  • Check-in received
  • Check-in missed
  • Escalation triggered
  • Escalation confirmed
  • Session cancelled

Purpose

  • Preserve session history
  • Separate events from current session state
  • Support future escalation workflows
  • Improve traceability

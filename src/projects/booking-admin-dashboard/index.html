Booking & Operations Admin Dashboard

Full-Stack Booking Management Application

  • Industry: Business Operations
  • Type: Full-Stack Web Application
  • Tech: Java, Spring Boot, React, PostgreSQL, Docker
View GitHub Repo

Overview

The Booking & Operations Admin Dashboard is a full-stack application for managing bookings, services, staff, customers, and operational data through one centralized system.

The application supports both registered customers and guest bookings while giving administrators structured control over the resources required to manage daily booking operations.

The project focuses on the business logic behind real-world scheduling rather than only providing a basic CRUD interface.

Challenge

Booking systems need to coordinate several connected resources at the same time.

Common operational problems include:

  • Conflicting bookings for the same staff member
  • Services with different durations and requirements
  • Managing both registered and guest customers
  • Keeping staff and customer records synchronized
  • Maintaining consistent booking data across the system

The challenge was to build a system that:

  • Centralizes booking administration
  • Prevents overlapping reservations
  • Associates bookings with services and staff
  • Supports registered and guest customers
  • Provides clear administrative workflows
  • Keeps business rules inside the backend

Solution

Architecture

The application uses a separated frontend, backend, and relational database architecture.

Frontend

  • React
  • Vite
  • Administrative dashboard views
  • Dynamic forms and filtered data

Backend

  • Java
  • Spring Boot
  • REST API
  • Service-layer business logic
  • DTO-based request and response handling

Database & Environment

  • PostgreSQL
  • Flyway migrations
  • Docker Compose
  • Relational persistence

Business rules remain in the backend instead of being dependent on frontend validation.

Domain Design

Core Entities

  • Users
  • Staff profiles
  • Services
  • Bookings

Relationships

  • Bookings reference a service
  • Bookings reference assigned staff
  • Bookings track their creator
  • Bookings can reference registered customers
  • Guest bookings use fallback customer information

This model separates authentication data, staff-specific information, bookable services, and reservation data.

Booking Logic

Booking creation requires more than storing a date and time. The backend validates whether the requested reservation is operationally valid.

Validation

  • Service selection
  • Staff assignment
  • Booking start time
  • Booking duration
  • Time overlap detection
  • Cancellation rules

Customer Handling

  • Registered customer bookings
  • Guest customer fallback
  • Creator tracking
  • Customer information management

Centralizing these rules ensures that invalid bookings cannot bypass validation through the frontend.

Administrative Dashboard

The React frontend provides dedicated administrative views for the main operational areas.

Bookings

  • Create bookings
  • View booking data
  • Filter booking lists
  • Handle registered customers
  • Handle guest customers

Services

  • Create services
  • Update service information
  • Manage bookable offerings

Staff

  • Manage staff profiles
  • Associate staff with bookings
  • Maintain operational staff data

Users

  • Manage user records
  • Maintain customer information
  • Support administrative account workflows

Business Rules

A central goal of the project was moving important booking decisions into explicit backend logic.

  • Staff cannot receive overlapping bookings
  • Booking duration is connected to the selected service
  • Referenced users, services, and staff must exist
  • Registered and guest bookings follow different customer handling paths
  • Cancellation is handled as part of the booking lifecycle

This creates predictable behavior regardless of which client consumes the API.

Database Design

PostgreSQL stores the operational data using a relational schema managed through Flyway migrations.

Data Structure

  • User accounts
  • Staff-specific profiles
  • Service definitions
  • Booking records

Design Goals

  • Referential integrity
  • Clear entity responsibility
  • Repeatable database migrations
  • Maintainable schema evolution

  • Filtered administrative views

Technical Highlights

  • PostgreSQL relational database
  • Flyway database migrations

Project Purpose

The project demonstrates how a typical booking application becomes an operational system once scheduling rules, resource relationships, customer variations, and administrative workflows are handled together.
